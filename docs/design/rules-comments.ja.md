# ルール: `comments/`

## 目的

次の人や次のエージェントは、コメントをコードについての事実として読む。コメントがコードと食い違ったり、欠けたりする原因になる書き方が3つある。いつとは言わない「後で」やるというメモ、説明の無い公開のコード、もう無い文書への参照だ。`comments/` ルールは、変更がこのどれかを足すのを止める。

## ルール

| ルール | 種類 | 後退になるとき |
|---|---|---|
| `comments/todo-format` | 見つけるルール | `TODO`、`FIXME`、`XXX` で始まるコメントの行が、設定した形になっていない |
| `comments/missing-doc` | 見つけるルール | 製品のコードの公開された関数・メソッド・型に doc コメントが無い |
| `comments/broken-reference` | 見つけるルール | コメントが、その版に存在しない Markdown ファイルを指している |

どれも既定で有効。生成されたファイルは決して検査しない。

### `comments/todo-format`

- **見つけるもの**: （コメントの記号と空白の後が）`TODO`、`FIXME`、`XXX` で始まり、`rules.comments.todo` に合わないコメントの行
- **既定の形**: `TODO(<いつ、または誰が>): <何を>` — 正規表現は `^TODO\([^)]+\): \S`。`FIXME` と `XXX` は決して合わないので、常に見つかったものになる。「後で」を表す語は1つで足りる
- **なぜ困るか**: いつやるかの書かれていない TODO は、誰も手を付けないまま残りやすい。残った TODO は、何が終わっているかについて読み手を誤らせる
- **直し方**: いつか誰がやるかを書く（`TODO(stage 2): …`）か、今やるか、消す
- 製品は `^TODO\(stage[0-9]+\): \S` のような自分の形を決める。形の変更には人の確認が要る。新しい形のほうが厳しいかを hadome は判断できないからだ
- アンカーはコメントの行の文字列なので、コメントを動かしても新しいものにはならない

### `comments/missing-doc`

- **見つけるもの**: doc コメントの無い、公開された関数、公開された型のメソッド、公開された型（インターフェースを含む）
- **なぜ困るか**: 呼ぶ側は本体の代わりに doc コメントを読む。それが無いと、呼ぶ側はみな実装を読んで推測する
- **直し方**: 名前で始まる1文を書き、何をするか（何であるか）と、呼ぶ側が書かれていないと誤ることを書く
- テストのコードは検査しない。テストは誰にも呼ばれない
- アンカーはシンボルの ID

### `comments/broken-reference`

- **見つけるもの**: コメントの中の `.md` で終わる語（後に `#section` が続いてもよい）のうち、その版に存在しないファイルを指すもの
- **解決の仕方**: `./` か `../` で始まる参照はコメントのあるファイルからの相対、それ以外はリポジトリのルートからの相対
- **なぜ困るか**: 読み手は、設計書への参照があれば、理由がその文書に書いてあると考える。参照先が無いと、その理由を読めない
- **直し方**: 文書の今のパスを指すか、参照を消す
- 確かめるのはファイルだけで、`#` の後の節は確かめない
- アンカーは書かれたとおりの参照

## 設定

```yaml
rules:
  comments:
    todo: '^TODO\(stage[0-9]+\): \S'   # TODO が取るべき形
```

`todo` は正しい正規表現でなければならない。正しくないものは設定の誤り（終了コード `2`）になる。

## 事実

| 事実 | 使い道 |
|---|---|
| `Comment`（パス、行、文字列）と `File.Role` | `todo-format`、`broken-reference`。`Directive` の印が付いたコメント（`//go:embed`、`//line`）は文章ではなく道具への指示なので飛ばす |
| `Symbol.Exported`、`Symbol.Doc`、`Symbol.Kind`（`type` を含む） | `missing-doc` |

## 自己テストの事例

| ルール | 事例 |
|---|---|
| `comments/todo-format` | 新しい形の無い TODO は落ちる · 形どおりの TODO は通る · FIXME は落ちる · 動いただけの既存の形の無い TODO は通る · 文の途中の "TODO" は通る · 製品自身の形が当たる |
| `comments/missing-doc` | doc コメントの無い新しい公開の関数は落ちる · 公開されていないものは通る · 公開されていない型のメソッドは通る · doc コメントの無い公開の型は落ちる · テストファイルは検査しない |
| `comments/broken-reference` | 無いファイルへの参照は落ちる · 存在するファイルへの参照は通る · 相対の参照はファイルから解決する · コメントが指す文書を消すと落ちる · ディレクティブは参照ではない · URL は参照ではない |

## 不変条件

1. 生成されたファイルは決して検査しない
2. base に既にあるコメントは、どこへ動いても止めない

## 意図して入れなかったもの

- doc コメントが正確かを確かめること。ルールでは確かめられないので、レビューとエージェントへの指示に任せる
- Markdown ファイルの中の `#section` のアンカーを確かめること
- 別の形の参照（URL、`see foo.go`）。設計の記録は Markdown の文書だけだ
