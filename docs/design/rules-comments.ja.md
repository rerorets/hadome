# ルール: `comments/`

## 目的

`comments/` ルールは変更が次の3つの書き方のどれかを足すのを止めます。どれも、コメントがコードと食い違ったり、欠けたりする原因になる書き方です。

- いつとは言わずに「後で」やるというメモ
- 説明の無い公開のコード
- もう無い文書への参照

次の人や次のエージェントは、コメントをコードについての事実として読みます。

## ルール

| ルール | 種類 | 後退になるとき |
|---|---|---|
| `comments/todo-format` | 見つけるルール | `TODO`、`FIXME`、`XXX` で始まるコメントの行が、設定した形になっていない |
| `comments/missing-doc` | 見つけるルール | 製品のコードの公開された関数・メソッド・型に doc コメントが無い。値（Terraform の `variable` と `output`、Ansible のロールの defaults の変数）に説明が無い |
| `comments/broken-reference` | 見つけるルール | コメントが、その版に存在しない Markdown ファイルを指している |

どれも既定で有効です。生成されたファイルは、決して検査しません。

### `comments/todo-format`

- **見つけるもの**: コメントの記号と空白の後が `TODO`、`FIXME`、`XXX` で始まり、`rules.comments.todo` に合わないコメントの行
- **既定の形**: `TODO(<いつ、または誰が>): <何を>` です。正規表現は `^TODO\([^)]+\): \S` です。`FIXME` と `XXX` は決して合わないので、常に違反になります。「後で」を表す語は1つで足ります。
- **なぜ困るか**: いつやるかの書かれていない TODO は、誰も手を付けないまま残りやすくなります。残った TODO は、何が終わっているかについて読み手を誤らせます。
- **直し方**: いつやるか、または誰がやるかを書きます（例: `TODO(stage 2): …`）。または、今やるか、消します。
  - 違反の直し方の文には、設定した形と、その形に合う例を書きます。例は、よくある形（`TODO(stage 2): …`、`TODO(#123): …`、`TODO(alice): …` など）のうち、設定した形に合う最初のものです。どれも合わなければ、例は書きません
- 製品は `^TODO\(stage[0-9]+\): \S` のような自分の形を決めます。形の変更には、人の確認が要ります。新しい形のほうが厳しいかを、hadome は判断できないからです。
- アンカーはコメントの行の文字列です。そのため、コメントを動かしても新しいものにはなりません。

### `comments/missing-doc`

- **見つけるもの**: doc コメントの無い、公開された関数・公開された型のメソッド・公開された型（インターフェースを含む）
- **なぜ困るか**: 呼ぶ側は本体の代わりに doc コメントを読みます。doc コメントが無いと、呼ぶ側はみな実装を読んで推測します。
- **直し方**: 名前で始まる1文を書きます。書くのは、何をするか（何であるか）と、書かれていないと呼ぶ側が誤ることです。
  - TypeScript・JavaScript・Java・Kotlin の doc コメントは `/** */` です。`//` の行コメントは doc コメントに数えません。直し方の文にもそう書きます。
- **doc コメントを求めないもの**: 決まりにより、説明がほかの場所にあるメソッドです（`Symbol.DocElsewhere`）。

  | 言語 | メソッド | 説明がある場所 |
  |---|---|---|
  | Kotlin | `override fun` | 上書きされる宣言 |
  | Java | `@Override` の付いたメソッド | 上書きされる宣言 |
  | TypeScript | `override` の付いたメソッド | 上書きされる宣言 |
  | TypeScript | クラスの `constructor` | クラスの doc コメント |
  | Go | 標準ライブラリのインターフェースが決めるメソッド（下の一覧） | そのインターフェース |

  - Go のメソッドは、名前と、引数と戻り値の型の両方が一覧に合うときだけ外します。例: `Len() int` は外しますが、`Len() int64` には doc コメントを求めます。
  - Go の一覧: `Error() string`、`String() string`、`ServeHTTP(http.ResponseWriter, *http.Request)`、`Unwrap() error`、`Unwrap() []error`、`Is(error) bool`、`As(any) bool`、`Format(fmt.State, rune)`、`MarshalJSON() ([]byte, error)`、`UnmarshalJSON([]byte) error`、`MarshalText() ([]byte, error)`、`UnmarshalText([]byte) error`、`Len() int`、`Less(int, int) bool`、`Swap(int, int)`
  - Java のコンストラクタと、TypeScript で `override` を書いていない上書きには、doc コメントを求めます。上書きかどうかを、宣言だけからは言えないからです。
- 値（種類 `value` のシンボル）は、doc コメントではなく説明を見ます（[adapters-iac.ja.md](adapters-iac.ja.md)）。なぜ困るかと直し方も、値のためのものを出します。
  - **なぜ困るか**: 値を渡す側も読む側も、値を使うコードではなく説明を読みます。説明が無ければ、みなそのコードを読んで、何のための値かを推し量ることになります。
  - **直し方**: 何のための値か、書かなければ使う側が取り違えることを、説明に書きます。書く場所は、Terraform なら `description` の引数、Ansible ならロールの `meta/argument_specs.yml` にあるその変数の `description` です。
- **フレームワークの入口**: フレームワークが名前で呼ぶ関数にも、doc コメントを求めないことにできます。例: SvelteKit の `+page.ts` の `load`、関数のホスティングの `functions/` の下の `onRequest…`。これらはフレームワークの文書が説明していて、製品のコードから呼ぶ人はいないからです。
  - 設定の `rules.comments.entry-points` に、名前とパスの組を並べます（下の「設定」）
  - 項目の `names` は、シンボルの名前の glob です。名前は、ユニットを除いたものです。関数なら `load`、メソッドなら `Store.Append` です
  - 項目の `paths` は、ファイルのパスの glob です。省くと、どのファイルにも当てます
  - 1つの項目の `names` のどれかと `paths` のどれかの両方に合うシンボルには、doc コメントを求めません
  - 項目を足すと、doc コメントを求めないシンボルが増えます。そのため、足すには人の確認が要ります（`config/loosened`、終了コード `3`）。項目の中身を変えるのも、足したものとして数えます
- テストのコードは検査しません。テストは誰にも呼ばれないからです。
- アンカーはシンボルの ID です。

### `comments/broken-reference`

- **見つけるもの**: コメントの中の `.md` で終わる語のうち、その版に存在しないファイルを指すもの。語の後に `#section` が続いてもかまいません。
- **解決の仕方**: 参照の形で、探す場所が違います。

  | 参照の形 | 例 | 探す場所 |
  |---|---|---|
  | `./` か `../` で始まる | `./README.md` | コメントのあるファイルからの相対 |
  | それ以外で `/` を含む | `docs/design/store.md` | リポジトリのルートからの相対 |
  | `/` を含まない（ファイルの名前だけ） | `orders.md` | リポジトリのどこか。同じ名前のファイルが1つでもあれば、存在するとみなします |

  - ファイルの名前だけの参照は、たいてい近くにある文書を指しています。どれを指すかは決められないので、同じ名前のファイルがあれば通します。
  - ファイルの名前だけの参照を探すとき、アダプタが読まないディレクトリ（`vendor`、`node_modules`、`.` で始まるものなど）は探しません。
  - 読まないディレクトリの一覧は、アダプタの一覧（`walk.Skip`）の写しです。ルールはアダプタを import できないので、写しを持ちます。2つの一覧が違うと、テスト（`internal/adapter` の `TestBrokenReferenceSkipsTheDirectoriesTheAdaptersSkip`）が落ちます。
- **参照の区切り**: 参照は、行の初め、空白、括弧、引用符の後から始まります。日本語の区切り（`・`、`、`、`（`、`「`、`『`、`【`、`：`、全角の空白）の後も同じです。例: `設計（docs/design/store.md）` の参照も拾います。
- **なぜ困るか**: 読み手は、設計書への参照があれば、理由がその文書に書いてあると考えます。参照先が無いと、その理由を読めません。
- **直し方**: 文書の今のパスを指すか、参照を消します。
- 確かめるのはファイルだけです。`#` の後の節は確かめません。
- アンカーは書かれたとおりの参照です。

## 設定

```yaml
rules:
  comments:
    todo: '^TODO\(stage[0-9]+\): \S'   # TODO が取るべき形
    entry-points:                      # doc コメントを求めないフレームワークの入口
      - names: [load]
        paths: ["**/+page*.ts"]
      - names: ["onRequest*"]
        paths: ["functions/**"]
```

`todo` は正しい正規表現でなければなりません。正しくない正規表現は、設定の誤り（終了コード `2`）になります。

`entry-points` の `names` と `paths` は、正しい glob でなければなりません。正しくない glob は、設定の誤り（終了コード `2`）になります。`names` は1つ以上要ります。

## 事実

| 事実 | 使い道 |
|---|---|
| `Comment`（パス、行、文字列）と `File.Role` | `todo-format`、`broken-reference`。`Directive` の印が付いたコメント（`//go:embed`、`//line`）は、文章ではなく道具への指示なので飛ばします |
| `Symbol.Exported`、`Symbol.Doc`、`Symbol.DocElsewhere`、`Symbol.Kind`（`type` を含む）、`File.Unit` | `missing-doc`。`File.Unit` は、入口の名前からユニットを除くために使います |

## 不変条件

1. 生成されたファイルは、決して検査しません。
2. base に既にあるコメントは、どこへ動いても止めません。

## 意図して入れなかったもの

- doc コメントが正確かを確かめること。ルールでは確かめられないので、レビューとエージェントへの指示に任せます。
- Markdown ファイルの中の `#section` のアンカーを確かめること
- 別の形の参照（URL、`see foo.go`）。設計の記録は Markdown の文書だけです。
