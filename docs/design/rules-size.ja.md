# ルール: `size/`

## 目的

`size/` ルールはファイル・関数・インターフェースの大きさに上限を置きます。ほかのルールと同じく、チェックを落とすのは、変更が悪くしたものだけです。上限を置くのは、人やエージェントが一度に読み切れる大きさを超えたコードは、全体を理解しないまま変えられやすいからです。

## ルール

| ルール | 測るもの | 既定の上限 |
|---|---|---|
| `size/file-lines` | ソースファイルの行数 | 400 |
| `size/function-lines` | 関数やメソッドの行数（宣言から閉じ括弧まで） | 60 |
| `size/params` | 関数やメソッドの引数の数（レシーバは数えない） | 5 |
| `size/complexity` | 関数やメソッドの循環的複雑度 | 15 |
| `size/interface-methods` | インターフェースのメソッドの数 | 5 |

どれも見つけるルールで、既定で有効です。

- **見つけるもの**: 上限を超えたファイル・関数・インターフェース
- **なぜ困るか**: 上限を超えると、コードは一度に読み切れなくなります。全体を理解しないまま、変更が入ります。
- **直し方**: もともとある切れ目で分けます。例: 手順ごとにヘルパー、関心ごとに型。上限を上げるのは、人が確認する設定の変更です。

循環的複雑度は 1 に `if`、`for`、`case`（`default` は除く）、`&&`、`||` をそれぞれ1ずつ足した数です。各アダプタは自分の言語の分岐をこの数え方に当てはめて数えます。

### 入れ子の関数

関数の中の関数は、外の関数とは別に数えます。ESLint の `complexity` と同じ数え方です。入れ子の関数とは、アロー関数、ラムダ、クロージャ、Go の関数リテラル、入れ子の `def`、無名クラスのメソッドなどです。

- **外の関数**: 自分の分岐だけを数えます。入れ子の関数の中の分岐は足しません。例: 自分には分岐がなく、`if` が16個あるアロー関数を持つ関数の複雑度は 1 です。
- **入れ子の関数**: それぞれ自分の分岐だけで数え、同じ上限を当てます。入れ子の入れ子も、それぞれ別に数えます。
- **上限を超えた入れ子の関数の報告**: 外側のシンボル（関数かメソッド）の違反として報告し、メッセージに入れ子の関数の行を書きます。例: 「`setup` の 4 行目の関数: 循環的複雑度 16（上限 15）」。違反の行も入れ子の関数の行にします。

入れ子の関数を外側のシンボルに付けるのは、名前のある入れ子の関数（`const onMessage = () =>`）も無名のものも、6つの言語で同じ形で報告するためです。入れ子の関数を自分のシンボルにすると、ほかのルール（`size/function-lines` や `comments/` など）にも新しいシンボルが現れます。

base との照合では、入れ子の関数の違反は外側のシンボルで照合します。行の番号は照合に使いません。そのため、入れ子の関数が動いただけでは後退になりません。同じ外側のシンボルの中で上限を超えた入れ子の関数が増えるか、どれかの値が大きくなると後退です。外の関数自身の違反とは別に照合します。

数え方を変えても、base と head は同じ数え方で測ります。そのため、変えていないファイルの数が変わって後退になることはありません。

### 測るもの

測るのは製品のコードだけです。ソースファイルと、その中のシンボルを測ります。テストファイルと生成されたファイルは測りません。テストは事例の表などでもともと長くなります。生成されたコードは、誰も分けられません。

### 悪くなれば後退

違反のアンカーはファイルかシンボルです。そのため、base に既にある違反は、行がどう動いても止めません。

違反は**測った値**も持ちます。head の違反が base のものと照合され、値が大きくなっていれば後退です。例: 80行の関数が90行に伸びると落ち、75行に縮むと通ります。

これは測った値を持つ違反に対するエンジンの一般的な規則で、`size/` が独自にしていることではありません。規則は [engine.ja.md](engine.ja.md) にあります。

### ファイルの行数の違反が指す行

`size/file-lines` の違反は、上限を超えた最初の行を指します。例: 上限が 300 なら、301 行目です。`text` は `store/store.go:301` と書き、`json` は `line` を `301` にします。

- **行の決まり方**: 行は上限だけで決まります。ファイルの中身では決まりません。そのため、どの言語のファイルでも同じ行になります。
- **行を持たせる理由**: 行が無いと、エディタや CI の注釈はファイルの先頭を指します。上限を超えた最初の行なら、どこから先が上限を超えた分かが分かります。
- **base との照合**: 違反のアンカーはファイルです。行は照合に使いません。そのため、上限を変えて行が変わっても、それだけでは後退になりません。
- **例外の印**: ほかのルールと同じく、印のある行とその次の行に当てはまります。そのため、印は報告された行か、その1つ前の行に書きます。例: 上限が 300 なら、300 行目か 301 行目です。印より上に行を足したり、上限を変えたりして印が外れると、印は何も抑えなくなります。このときは、違反と `engine/marker-unused` の両方が報告されます。

## 設定

```yaml
rules:
  size:
    file-lines: 300           # 5つのどれでもよい。省いたキーは既定のまま
    function-lines: 60
    params: 5
    complexity: 15
    interface-methods: 5
```

- 高い上限は低い上限より緩い扱いです。そのため、上限を上げるには人の確認が要ります（終了コード `3`）。下げるときは要りません。
- 上限は head の設定から取り、両方の版に当てます（[configuration.ja.md](configuration.ja.md)）。そのため、上限を下げても、報告されるのは変更が足したものだけです。もともと超えていたものは報告されません。

## 事実

| 事実 | 使い道 |
|---|---|
| `File.Lines`、`File.Role` | `size/file-lines` |
| `Symbol.EndLine`、`Symbol.Params`、`Symbol.Complexity`、`Symbol.Nested` | 関数とメソッド。`Nested` は入れ子の関数ごとの行と複雑度 |
| `Symbol.Kind` = `interface`、`Symbol.Methods` | `size/interface-methods` |

## 自己テストの事例

| ルール | 事例 |
|---|---|
| `size/function-lines` | 新しい長い関数は落ちる · 動いただけの既存の長い関数は通る · 伸びた既存の長い関数は落ちる · 縮んだものは通る · 長いテスト関数は通る |
| `size/file-lines` | 上限を超えて伸びたファイルは落ちる · 上限を超えたまま変えていないファイルは通る · 生成されたファイルは通る · 上限を超えた最初の行の例外の印は、そのファイルの違反を抑える |
| `size/params` | 引数の多すぎる新しい関数は落ちる · 引数が5つなら通る |
| `size/complexity` | 分岐の多すぎる新しい関数は落ちる · 上限ちょうどの関数は通る · `default` は分岐に数えない · 入れ子の関数の分岐は外の関数に足さない · 分岐の多すぎる新しい入れ子の関数は落ちる · 変えていない入れ子の関数は通る |
| `size/interface-methods` | 新しい幅の広いインターフェースは落ちる · メソッドが5つのインターフェースは通る |
| （設定） | 下げた上限は新しいコードだけを報告する · 上げた上限は人の確認が要る |

## 不変条件

1. 上限は製品のコードにだけ当てます。テストと生成されたコードは、決して測りません。
2. base にある違反は、変更がそれを大きくしない限り止めません。

## 意図して入れなかったもの

- パスごとの上限。例: フロントエンドのディレクトリには、もっと小さい上限を置く。
- 「論理的な」行を数えること。「論理的な」行とは、コメントや空行を除いた行です。読み手が読むのは、画面上の行です。
