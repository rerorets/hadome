# ルール: `tests/`

## 目的

`tests/` ルールは、エージェントがテストを変えていっても、テストを信じられる状態に保つ。確かめるのは2つ。

- **テストの書き方** — 何も証明せずにテストを通してしまう癖
- **テストが守るもの** — 変更がそれを黙って狭められないように

ルールは言語のアダプタが出す事実（[adapters.ja.md](adapters.ja.md)）の上で動き、言語を知らない。

## ルール

| ルール | 種類 | 後退になるとき |
|---|---|---|
| `tests/no-clock` | 見つけるルール | テストが時刻を直接読む |
| `tests/no-sleep` | 見つけるルール | テストが sleep で待つ |
| `tests/skip-without-reason` | 見つけるルール | テストが理由なしにスキップ・無効化されている |
| `tests/always-true` | 見つけるルール | assert が落ちようがない |
| `tests/no-mock` | 見つけるルール | *純粋な*ユニットのテストがモックを使う |
| `tests/purity-lost` | 見つけるルール（人の確認） | base で純粋だったユニットが head で純粋でない。終了コードは `3` で、`1` にはならない |
| `tests/scope-shrunk` | 測るルール | base で守られていたものが、head でどのテストにも守られていない |
| `tests/target-unknown` | 見つけるルール（人の確認） | 新しい有効なテストの対象がまったく特定できない。終了コードは `3` で、`1` にはならない |
| `tests/invariant-unguarded` | 見つけるルール | 有効にした不変条件を守る有効なテストが無い |

どれも既定で有効で、設定は要らない。

## テストの書き方

この4つのルールは、アダプタの危険の分類の上で動く。見つかったもののアンカーは、テストの名前と、正規化した該当の行なので、テストを動かしても新しいものにはならない。

### `tests/no-clock`

- **見つけるもの**: テストの中の `clock` の危険
- **なぜ困るか**: テストの結果が実行する時刻で変わる。今日は通っても、深夜0時、月末、別のタイムゾーンで落ちる
- **直し方**: 時刻を値として渡すか、時計を注入する
- 製品は自前の時計のラッパーを危険の表に足すので、それを迂回したものも捕まる

### `tests/no-sleep`

- **見つけるもの**: テストの中の `sleep` の危険
- **なぜ困るか**: sleep は長すぎる（テストが遅い）か短すぎる（結果が揺れる）かのどちらかで、実際の出来事を待つことはない
- **直し方**: 出来事そのものを待つ（チャネル、コールバック、期限つきで期限切れなら派手に落ちる条件）

### `tests/skip-without-reason`

- **見つけるもの**: 理由が無いか空のスキップ
- **なぜ困るか**: スキップしたテストは何も守らない。理由が無ければ、いつ戻すべきか誰も決められない
- **直し方**: スキップそのものに理由を書く: `t.Skip("…")`、`pytest.skip(reason="…")`、`@Disabled("…")`、`#[ignore = "…"]`、または `it.skip` の行かその上のコメント。メッセージの例は、テストのファイルの言語の書き方で出す
- 一部の場合だけのスキップ（`if runtime.GOOS == "windows"`）にも理由が要る
- 理由の**ある**スキップはここでは後退ではないが、そのテストは守る範囲（後述）に数えなくなる

### `tests/always-true`

- **見つけるもの**: `always-true` の危険 — 定数に対する assert や、値をそれ自身と比べるもの
- **なぜ困るか**: assert が落ちようがないので、コードが何をしてもテストは成功を報告する
- **直し方**: テストしている振る舞いに対して assert する

### `tests/no-mock`

- **見つけるもの**: 対象がすべて*純粋な*ユニットにあるテストの中の `mock` の危険
- **なぜ困るか**: 純粋なユニットには副作用が無い。モックが要るなら副作用が入り込んでいて、モックがそれを隠している
- **直し方**: 副作用をユニットの外へ出し、ユニットは素の値でテストする
- どのユニットが純粋かは、hadome が検査のたびに決める（後述）。設定するものは無い
- 純粋でない（または純粋さが `unknown` の）ユニットも呼ぶテストは、そのユニットのためにモックが要るかもしれないので、報告しない

### 純粋なユニット

**純粋なユニット**は、入力を受けて結果を返し、外の世界に触れない。データベース、ネットワーク、ファイル、時計、環境のどれにも触れない。価格の計算、検証、日付の範囲の計算が典型だ。純粋でないコードは本物の依存でテストする（統合テスト）のがよく、純粋なコードは素の値でテストするのがよい。

hadome は純粋さを import から、検査のたびに決める。

- 入出力をするものを何も import せず、純粋でないユニットにも依存しないユニットは**純粋**
- 何が入出力をするかは、危険の表と同じく各アダプタの `io` の表が決める（Go: `net`、`os`、`database/sql`、…。Python: `socket`、`requests`、`sqlite3`、…）。設定で項目を足せるが、消せない。項目はユニット（`example.com/acme/db`）か、ユニットの後に `/...` を付けたもの（そのユニットと配下すべて、`example.com/acme/clients/...`）。製品のデータベース層のような、リポジトリ自身のユニットを項目にしてもよい。そのときはそれを import するものすべてが純粋でなくなる
- import をすべて特定できないユニットは `unknown` で、`unknown` は決して純粋ではない
- 純粋さはリポジトリ自身の import を推移的にたどる。純粋でないユニットを import するユニットも純粋でない
- Go の `time` パッケージは表に無い。素の値（`time.Duration`）も持つからだ。テストで時刻を読むことは純粋さではなく `tests/no-clock` が捕まえる

### `tests/purity-lost`

- **項目**: ある版の純粋なユニット。項目が消えると人の確認が要る測るルール
- **見つけるもの**: base で純粋で、head で純粋でないユニット
- **なぜ困るか**: 純粋だったコードに副作用が入った。意図したこともあるが、設計の滑りであることが多い
- **扱い**: 終了コード `3`（人が確認する）を返し、`1` にはならない
- **正当な削除**: そのユニットが head にもう無い
- `io` の表は両方の版で head の設定から取るので、項目を足しても、もともとそれを import していたユニットの確認を求めることはない

## テストが守るもの

### 守る範囲

守る範囲は、少なくとも1つの有効なテストが動かす**対象**の集合だ。対象とは、テスト以外のコードにある公開の関数やメソッドのうち、テストが呼ぶものとしてアダプタが推定したものを言う。

テストを数えるのは有効なときだけだ。スキップしたテスト（理由の有無を問わない）は何も守らない。

### `tests/scope-shrunk`

- **項目**: 守られている対象ごとに1つ。対象のユニットと名前をキーにする
- **後退**: base で守られていた対象が head で守られていない
- **正当な削除**: 対象そのものが head にもう無い（コードが消された、または名前が変わった）。hadome がこれを確かめるので、誰も宣言しなくてよい
- **整理として通るもの**: 重複したテストをまとめる、新しく何も守らないテストを消す、テストを動かす・名前を変える — 守られている対象の集合は変わらない
- **特定できないもの**: 対象がまったく特定できないテストは `tests/target-unknown` が報告し、終了コード `3` を返す。テストファイルのヘルパー関数を通ってコードに届くテストは、ヘルパーの中までたどるので、ヘルパーがあっても対象は特定できなくならない

ミューテーション解析が入ると、項目は「テストが捕まえる壊れ方」になり、このルールは名前も意味も変えずに鋭くなる。

### 不変条件を守るテストの見つけ方

人やエージェントが、どのテストがどの不変条件を守るかを言う必要はほとんどない。hadome が見つける。

| 不変条件 | 守るテストの見つけ方 |
|---|---|
| 組み込みの型 | **形から自動で。** テストの呼び出しが型に合えば、そのテストが不変条件を守る（下の表）。宣言は要らない |
| 製品固有の不変条件（`id` と `says`） | **宣言で。** テストの doc コメントに `guards: <id>` を書く。文の意味は形から分からないので、宣言が要るのはここだけ |

| 組み込みの型 | テストが守るとみなす条件（すべての対象について） |
|---|---|
| `idempotent` | 対象を2回以上呼ぶ |
| `round-trip` | 対象を呼ぶ（なので組の両方の操作を呼ぶテストが守る） |
| `isolated` | 対象を少なくとも2つの異なるスコープ（後述）で呼ぶ |
| `durable`、`erasable`、`append-only`、`fail-closed` | 対象を呼び、`guards: <type> <target>` を書いている（構文だけでは確かな形がまだ無いので、宣言が要る） |

数えるのは有効なテストだけだ。常にスキップされるテストは何も守らない。一部の場合だけスキップするテストは守る。

アダプタは、テストが呼ぶ対象ごとに、**何回**呼ぶかと、**いくつの異なるスコープ**で呼ぶかを報告する。

- **回数**は呼び出し箇所を数え、テストが呼ぶヘルパーの中の箇所も含む。ループの中の呼び出し箇所は2回と数える。2回以上実行されるからだ（表で回すテスト）
- 呼び出しの**スコープ**は、対象のスコープの引数に渡した値だ。スコープの引数とは、名前に `user`、`tenant`、`owner`、`account`、`org`、`team`、`workspace`、`customer`、`project` のどれかを含む最初の引数（大文字小文字を区別しない）、無ければリクエストのコンテキストでない最初の引数。異なるスコープは、その引数の正規化したソースの文字列で数える

設定に書く対象は、コードが呼ぶ形のとおり、ユニットと名前でシンボルを指す（`store.Append`、`store.Store.Len`）。パスの区切りの後にそれで終わる ID のシンボルすべてに当たるので、`api.CreatePost` は `example.com/app/api.CreatePost` に当たる。どのシンボルにも当たらない対象は守られていないと報告され、メッセージにもそう書かれる。

宣言はテストの doc コメントの1行 `guards: <invariant>` で、`<invariant>` は `hadome explain` やメッセージが呼ぶとおりに書く。製品固有の不変条件なら `id`、それ以外は `<type> <target>`（対象が複数なら `<type> <a>,<b>`）。

たまたま対象を2回呼んでいるだけのテストも、守るものとして数える。宣言を要らなくした代償だ。後でミューテーション解析が、形を「不変条件を壊したら実際にテストが落ちるか」に置き換える。

### `tests/invariant-unguarded`

- **見つけるもの**: 設定で有効にした不変条件のうち、守る有効なテストが無いもの
- **なぜ困るか**: 不変条件は書いてあるのに、何もそれを守らせていない
- **直し方**: 不変条件を確かめるテストを書く。形のある組み込みの型ならそれで済む。それ以外と製品固有の不変条件は、doc コメントに `guards:` を足す
- アンカーは不変条件なので、テストがどう動いても、見つかったものは版をまたいで照合される
- base と比べるので、テスト無しで新しい不変条件を有効にすると後退になる。base で既に守られていなかった不変条件は止めない
- **守りを失うのも同じ見つかったものだ。** 最後に守っていたテストが消える、スキップされる、形に合わなくなる、`guards:` の行を失うと、base で守られていた不変条件が head で守られていなくなる。新しい見つかったものなので後退になる。守りを別のテストに移しても、不変条件は守られたままなので何も変わらない
- **不変条件そのものを**設定から消すのはこのルールの仕事ではない。それは `config/loosened` で終了コード `3` を返す。約束をやめるのは人が決めることだからだ

（不変条件、守るテスト）の組に対する測るルールを別に作っても、まったく同じ場面で働くので作らない。

## 不変条件の候補

`hadome check` は、変更が足した不変条件の候補を一覧にする。ふつう不変条件を持つ場所だ（何かを作る操作 → `idempotent`、書き出しと読み込みの組 → `round-trip`、削除 → `erasable`、利用者やテナントで絞った読み出し → `isolated`）。参考情報で、終了コードは変えない。`hadome suggest` はすべてを出す。候補の見つけ方は [suggest.ja.md](suggest.ja.md)。

エージェント向けの指示のブロックは、大事な振る舞いに当たる候補を人に提案するようエージェントに伝えるので、誰もコマンドを実行しなくても候補は人に届く。

## メッセージ

見つかったものにはすべて、エージェント向けに書いた `why` と `fix` が付く。何が起きたか、なぜ困るか、それを解消するいちばん小さな変更だ。上の文章がそのメッセージの出発点になる。

## 自己テストの事例

各ルールには少なくとも次の事例が付く。

| ルール | 事例 |
|---|---|
| `tests/no-clock` | 新しく時刻を読むと落ちる · 既存のものをファイル内で動かすと通る · 文字列の中の時刻の読み出しは通る |
| `tests/no-sleep` | 新しい sleep は落ちる · テスト以外のコードの sleep はこのルールの仕事ではない |
| `tests/skip-without-reason` | 新しい理由なしのスキップは落ちる · 理由つきのスキップは通る · 空の理由は落ちる |
| `tests/always-true` | `assertTrue(true)` は落ちる · 値をそれ自身と比べると落ちる · 異なる2つの値を比べると通る |
| `tests/no-mock` | 純粋なユニットのテストのモックは落ちる · 純粋でないユニットのテストの同じモックは通る · 設定の `io` の項目で純粋でなくなったユニットは通る · リポジトリの純粋でないユニットを import するユニットは通る |
| `tests/purity-lost` | 純粋なユニットがデータベースの import を得ると `3` を返す · 一度も純粋でなかったユニットは返さない · import するユニットを通じて純粋でなくなると `3` を返す · 純粋なユニットを消すと通る |
| `tests/scope-shrunk` | 対象の唯一のテストを消すと落ちる · 1つの対象の2つのテストをまとめると通る · 対象とそのテストを消すと通る · テストの名前を変えると通る |
| `tests/invariant-unguarded` | テストの無い新しい不変条件は落ちる · 前から守られていない不変条件は止めない · 唯一の守りを消すと落ちる · 守りを別のテストに移すと通る · 唯一の守りをスキップすると落ちる · 不変条件を消すと `3` を返す（`config/loosened`） |
| `tests/invariant-unguarded`（形） | 唯一のテストが対象を1回しか呼ばない `idempotent` の不変条件は守られていない · 2回呼ぶテストは守る · `round-trip` には両方の操作が要る · `isolated` には2つのスコープが要る · 製品固有の不変条件は `guards:` でだけ守られる |

## 不変条件

1. 守るものを変えずにテストを動かす・名前を変える・まとめることで、これらのルールが落ちることはない
2. 常にスキップされるテストは、何かを守るものとして数えない。一部の場合だけ（あるプラットフォームで、あるフラグの下で）自分をスキップするテストは守る。そのスキップにも理由が要る
3. どのルールも、base に既にあるものを理由に変更を落とさない
4. これらのルールが特定できないものは報告し、黙って通さない

## 意図して入れなかったもの

- テストが*正しい*かを確かめること。近づけるのはミューテーション解析だけで、それは後で入る
- `tests/no-network`（予約）: テストから本物の外部サービスを呼ぶこと。アダプタがそうした呼び出しを特定できるようになったら足す
- テストの速さ（独自の設計を持つ別のルール群に属する）

## 決めたこと

1. 純粋さは hadome が検査のたびに import から決める。`tests/no-mock` に設定は要らない。純粋でなくなったユニットは終了コード `3` を返す。不変条件の候補は参考情報として `hadome check` の出力に出る
2. 形のある組み込みの不変条件の型を守るテストは自動で見つける。`guards:` が要るのは製品固有の不変条件と、形の無い型だけ。別の `tests/guard-shape` ルールは無い
3. `tests/no-network` は予約: テストは本物の外部サービスと通信してはいけない。アダプタがそうした呼び出しを特定できるようになったら足す
4. 不変条件を設定から消すと、消す変更で1回だけ終了コード `3` を返す。その変更が基準のブランチに入った後は、不変条件は単に無いだけで、後の変更は `0` を返す。終了コード `3` の場面はすべて同じ
