# ルール: `tests/`

## 目的

`tests/` ルールは、エージェントがテストを変えていっても、テストを信じられる状態に保ちます。確かめるのは次の2つです。

- **テストの書き方**: 何も確かめずにテストが通ってしまう書き方をしていないか
- **テストが守るもの**: 変更がそれを黙って狭めていないか

ルールは言語のアダプタが出す事実（[adapters.ja.md](adapters.ja.md)）の上で動きます。ルール自身は言語を知りません。

## ルール

| ルール | 種類 | 後退になるとき |
|---|---|---|
| `tests/no-clock` | 見つけるルール | テストが時刻を直接読む |
| `tests/no-sleep` | 見つけるルール | テストが sleep で待つ |
| `tests/skip-without-reason` | 見つけるルール | テストが理由なしにスキップ・無効化されている |
| `tests/always-true` | 見つけるルール | assert が落ちようがない |
| `tests/no-mock` | 見つけるルール | *純粋な*ユニットのテストがモックを使う |
| `tests/purity-lost` | 測るルール（人の確認） | base で純粋だったユニットが head で純粋でない。終了コードは `3` で、`1` にはならない |
| `tests/scope-shrunk` | 測るルール | base で守られていたものが、head でどのテストにも守られていない |
| `tests/target-unknown` | 見つけるルール（人の確認） | 新しい有効なテストの対象がまったく特定できない。終了コードは `3` で、`1` にはならない |
| `tests/invariant-unguarded` | 見つけるルール | 有効にした不変条件を守る有効なテストが無い |
| `tests/guards-nothing` | 見つけるルール | テストが製品のコードを1つも呼ばず、製品のコードの値も読まない |
| `tests/no-assertion` | 見つけるルール | テストに確かめる呼び出し（assert）が1つも無い |
| `tests/duplicate` | 見つけるルール | テストの本体が、ほかのテストと同じ |

どれも既定で有効で、設定は要りません。

## テストの書き方

各ルールがどの事実の上で動くかと、違反のアンカーは次のとおりです。

| ルール | 上で動く事実 | アンカー |
|---|---|---|
| `no-clock`、`no-sleep`、`always-true` | アダプタの危険の分類 | テストの名前と、正規化した該当の行。危険がほかのファイルのヘルパーにあるときは、そのファイルと該当の行 |
| `skip-without-reason` | スキップの事実 | テストの名前 |

どのアンカーも行番号を含みません。そのため、テストを動かしても新しいものにはなりません。

### `tests/no-clock`

- **見つけるもの**: テストの中の `clock` の危険
- **なぜ困るか**: テストの結果が実行する時刻で変わります。今日は通っても、深夜0時、月末、別のタイムゾーンで落ちます
- **直し方**: 時刻を値として渡すか、時計を注入します
- 製品は自前の時計のラッパーを危険の表に足します。そのため、ラッパーを迂回したものも捕まります

### `tests/no-sleep`

- **見つけるもの**: テストの中の `sleep` の危険
- **なぜ困るか**: sleep は長すぎる（テストが遅い）か、短すぎる（結果が揺れる）かのどちらかです。実際の出来事を待つことはありません
- **直し方**: 出来事そのものを待ちます。例: チャネル、コールバック、期限つきの条件（期限を過ぎたら失敗として落ちる）

### `tests/skip-without-reason`

- **見つけるもの**: 理由が無いか空のスキップ
- **なぜ困るか**: スキップしたテストは何も守りません。理由が無ければ、いつ戻すべきかを誰も決められません
- **直し方**: スキップそのものに理由を書きます。例: `t.Skip("…")`、`pytest.skip(reason="…")`、`@Disabled("…")`、`#[ignore = "…"]`、`it.skip` の行かその上のコメント。メッセージの例はテストのファイルの言語の書き方で出します
- 一部の場合だけのスキップ（`if runtime.GOOS == "windows"`）にも理由が要ります
- 理由のあるスキップは、このルールでは後退になりません。ただし、そのテストは守る範囲（後述）に数えなくなります

### `tests/always-true`

- **見つけるもの**: `always-true` の危険です。例: 定数に対する assert、値をそれ自身と比べるもの
- 呼び出しを含む式は、同じ字面でもそれ自身と比べたことにしません。`f(x)` を2回呼んで比べるのは、同じ入力から同じ結果になることを確かめるテストで、落ちることがあるからです
- **なぜ困るか**: assert が落ちようがないので、コードが何をしてもテストは成功を報告します
- **直し方**: テストしている振る舞いに対して assert します

### `tests/no-mock`

- **見つけるもの**: 対象がすべて*純粋な*ユニットにあるテストの中の `mock` の危険
- **なぜ困るか**: 純粋なユニットには副作用がありません。モックが要るなら、ユニットに副作用が入っています。モックを使うと、テストからはその副作用が見えなくなります
- **直し方**: 副作用をユニットの外へ出し、ユニットは素の値でテストします
- どのユニットが純粋かは、hadome が検査のたびに決めます（後述）。設定するものはありません
- 純粋でないユニットや、純粋さが `unknown` のユニットも呼ぶテストは報告しません。そのユニットのためにモックが要るかもしれないからです
- スパイもモックに数えます。例: `vi.spyOn`、`jest.spyOn`、Mockito の `@Spy`。スパイは呼び出しを見張るか、振る舞いを置き換えます。どちらも、純粋なコードなら返す値を確かめれば足ります。何をモックとみなすかは、言語ごとの危険の表にあります（[adapters-treesitter.ja.md](adapters-treesitter.ja.md)）

### 純粋なユニット

**純粋なユニット**は入力を受けて結果を返し、外の世界に触れないユニットです。データベース、ネットワーク、ファイル、時計、環境のどれにも触れません。典型的な例は、価格の計算、検証、日付の範囲の計算です。

- 純粋でないコードは本物の依存でテストする（統合テスト）のがよいです
- 純粋なコードは素の値でテストするのがよいです

hadome は純粋さを import から、検査のたびに決めます。

- 入出力をするものを何も import せず、入出力をするグローバルの API も使わず、純粋でないユニットにも依存しないユニットは**純粋**です
- グローバルの API は、import せずに使えて、入出力をする API です。例: TypeScript の `fetch`、`localStorage`。どれを数えるかは各アダプタが決めます（[adapters-treesitter.ja.md](adapters-treesitter.ja.md)）
- 何が入出力をするかは、各アダプタの `io` の表が決めます。危険の表と同じ扱いです。例: Go なら `net`、`os`、`database/sql`、…。Python なら `socket`、`requests`、`sqlite3`、…
- `io` の表には設定で項目を足せます。消すことはできません
- 項目に書けるのは、ユニット（`example.com/acme/db`）か、ユニットの後に `/...` を付けたもの（そのユニットと配下すべて。`example.com/acme/clients/...`）です
- 製品のデータベース層のような、リポジトリ自身のユニットを項目にしてもかまいません。そのときは、それを import するものがすべて純粋でなくなります
- import をすべて特定できないユニットは `unknown` です。`unknown` は決して純粋ではありません
- 純粋さはリポジトリ自身の import を推移的にたどって決めます。純粋でないユニットを import するユニットも純粋ではありません
- import の輪（互いに import し合うユニット）は、まとめて1つとして決めます。輪のどれかが入出力に届くと、輪のユニットはすべて純粋ではありません。輪の中では、どのユニットも残りのすべてを import しているのと同じだからです。答えは、どのユニットから見始めても変わりません
- 型だけの import は依存に数えません。例: TypeScript の `import type`。コンパイルすると消え、実行するコードの依存ではないからです
- Go の `time` パッケージは表にありません。素の値（`time.Duration`）も持つからです。テストで時刻を読むことは、純粋さではなく `tests/no-clock` が捕まえます

### `tests/purity-lost`

- **項目**: ある版の純粋なユニット。項目が消えると人の確認が要る、測るルールです
- **見つけるもの**: base で純粋で、head で純粋でないユニット
- **なぜ困るか**: 純粋だったコードに副作用が入りました。意図したこともありますが、意図しない設計の変化であることが多いです
- **扱い**: 終了コード `3`（人が確認する）を返します。`1` にはなりません
- **正当な削除**: そのユニットが head にもう無い
- `io` の表は両方の版で head の設定から取ります。そのため、項目を足しても、もともとそれを import していたユニットの確認を求めることはありません
- 報告は、head でユニットを純粋でなくした import を指します。文言には、その import が何に届くかを書きます。例: 「`src/ui` はもう純粋でない。import している `src/lib` が入出力をする `node:fs` を import している」。届く先は、入出力をする import、グローバルの API、行き先の分からない import、hadome がリポジトリのファイルに見つけられないユニットのどれかです

## 要らないテスト

テストを足しても、守る範囲が広がるとは限りません。次の3つのルールは何も確かめないテストと、ほかのテストの写しを止めます。

- どれも、base にすでにあるものは報告せず、変更で増えたものだけを報告します
- スキップしたテストは対象にしません
- 後退にするのは、確実に言えるものだけです。テストに次のどれかがあれば報告しません: 特定できない呼び出し、製品のコードの値を読むところ、読めない関数に渡したテストの道具

### `tests/guards-nothing`

- **見つけるもの**: 対象（`Calls`）が1つも無く、特定できなかった呼び出し（`Unresolved`）も、製品のコードの値を読むところ（`Reads`）も無いテスト。テストのファイルの中のヘルパーと、テストの補助のファイル（[adapters-treesitter.ja.md](adapters-treesitter.ja.md)）の関数を通した呼び出しは、対象に数えます
- **なぜ困るか**: 製品のコードを呼ばないので、製品のコードをどう変えてもテストの結果は変わりません。標準ライブラリや外部のライブラリだけを呼ぶテストも、これに当たります
- **直し方**: 確かめたい製品のコードの関数を呼びます。要らないテストなら消します
- 呼び出しの一部でも特定できなかったテストは報告しません。製品のコードを呼んでいるかもしれないからです。対象が1つも特定できないテストは `tests/target-unknown` が扱います
- 製品のコードの定数や埋め込んだデータを読むテストは報告しません。その値が変われば、結果も変わり得るからです
- HTTP のテストの道具でアプリを外から動かすテスト（`Test.Drives`）は報告しません。製品のコードの関数を呼ばないので、どの関数を守るかは言えません。それでも製品のコードは動かしています。読む道具は [adapters-treesitter.ja.md](adapters-treesitter.ja.md) にあります

### `tests/no-assertion`

- **見つけるもの**: 確かめる呼び出し（`Test.Asserts`）が1つも無いテスト。数えるのは、テストの本体と、テストのファイルの中のヘルパーの中です
- **なぜ困るか**: 呼ぶだけのテストは、製品のコードが誤った値を返しても通ります。落ちるのは、例外や panic が起きたときだけです
- **直し方**: 振る舞いを確かめる assert を書きます。例外が起きないことだけを確かめるテストなら、理由つきの例外の印を書きます
- テストの道具（Go の `t`、Python の `self` など）を、アダプタが中を読めない関数に渡したテスト（`Test.AssertsUnknown`）は報告しません。その関数の中で確かめているかもしれないからです
- 何を assert とみなすかは、言語ごとの表にあります（[adapters.ja.md](adapters.ja.md)）。表に無い assert の関数は設定の `rules.tests.assertions` で足せます。組み込みの項目は消せません
- 項目を足すと、ルールは緩くなります。何も確かめない関数を足しても、テストを通せてしまうからです。そのため、足す変更は `config/loosened` として人の確認を求めます

### `tests/duplicate`

- **見つけるもの**: 本体が同じテストの組
- 本体は名前・コメント・空白を除いた字句の並び（`Test.Body`）で比べます。パラメタ化したテストの入力（デコレータや注釈）も本体に含めます
- **なぜ困るか**: 同じことを2回確かめても、守る範囲は広がりません。振る舞いを変えるときに、同じ直しを2か所にする手間が増えます
- **直し方**: 片方を消します。別の入力を確かめるつもりだったなら、入力を変えます
- 入力（リテラル）が1つでも違えば、別のテストとして扱います
- 項目は量のルールと同じく本体の指紋ごとに1つで、値は同じ本体のテストの数です。数が増えたら後退です。テストの名前を変えても、新しいものにはなりません

## テストが守るもの

### 守る範囲

**守る範囲**は少なくとも1つの有効なテストが動かす**対象**の集合です。**対象**はテスト以外のコードにある公開の関数やメソッドのうち、テストが呼ぶものとしてアダプタが推定したものです。

テストを数えるのは、有効なときだけです。スキップしたテストは理由の有無を問わず何も守りません。

### `tests/scope-shrunk`

- **項目**: 守られている対象ごとに1つ。キーは対象のユニットと名前です
- **後退**: base で守られていた対象が、head で守られていない
- **正当な削除**: 対象そのものが head にもう無い（コードが消された、または名前が変わった）。対象がユニットそのもの（Ansible のロール）のときは、そのユニットが head にもう無い。これは hadome が確かめるので、誰も宣言しなくてかまいません
- **整理として通るもの**: 守られている対象の集合を変えない整理です。例: 重複したテストをまとめる、新しく何も守らないテストを消す、テストを動かす・名前を変える
- **特定できないもの**: 対象がまったく特定できないテストは、`tests/target-unknown` が報告し、終了コード `3` を返します
- テストファイルのヘルパー関数を通ってコードに届くテストは、ヘルパーの中までたどります。そのため、ヘルパーがあっても対象は特定できなくなりません
- HTTP のテストの道具でアプリを外から動かすテスト（`Test.Drives`）も報告しません。どの関数を守るかは言えませんが、毎回人に確かめてもらうほどのことではないからです。こうしたテストは関数を守るテストとしては数えません

### 不変条件を守るテストの見つけ方

どのテストがどの不変条件を守るかは hadome が見つけます。そのため、人やエージェントが書く必要はほとんどありません。見つけ方は、不変条件の意味が呼び出しの形から分かるかどうかで分かれます。

| 不変条件 | 守るテストの見つけ方 |
|---|---|
| 組み込みの種類 | **形から自動で。** テストの呼び出しが種類の形に合えば、そのテストが不変条件を守ります（下の表）。宣言は要りません |
| 製品固有の不変条件（`id` と `says`） | **宣言で。** テストの doc コメントに `guards: <id>` を書きます。文の意味は形から分からないので、宣言が要るのはここだけです |

| 組み込みの種類 | テストが守るとみなす条件（すべての対象について） |
|---|---|
| `idempotent` | 対象を2回以上呼ぶ |
| `round-trip` | 対象を呼ぶ（なので組の両方の操作を呼ぶテストが守る） |
| `isolated` | 対象を少なくとも2つの異なるスコープ（後述）で呼ぶ |
| `durable`、`erasable`、`append-only`、`fail-closed` | 対象を呼び、`guards: <type> <target>` を書いている（構文だけでは確かな形が無いので、宣言が要る） |

数えるのは有効なテストだけです。常にスキップされるテストは何も守りません。一部の場合だけスキップするテストは守ります。

アダプタは、テストが呼ぶ対象ごとに、何回呼ぶかと、いくつの異なるスコープで呼ぶかを報告します。

- **回数**は呼び出し箇所の数です。テストが呼ぶヘルパーの中の箇所も含めます。ループの中の呼び出し箇所は2回と数えます。2回以上実行されるからです（表で回すテスト）
- 呼び出しの**スコープ**は対象のスコープの引数に渡した値です
- **スコープの引数**は名前に `user`、`tenant`、`owner`、`account`、`org`、`team`、`workspace`、`customer`、`project` のどれかを含む最初の引数です。大文字小文字は区別しません。当たる引数が無ければ、最初の引数です。Go ではリクエストのコンテキスト `context.Context` を除きます
- 異なるスコープはその引数の正規化したソースの文字列で数えます

設定に書く対象は、コードが呼ぶ形のとおり、ユニットと名前でシンボルを指します（`store.Append`、`store.Store.Len`）。

- 対象は、パスの区切りの後がそれで終わる ID のシンボルすべてに当たります。例: `api.CreatePost` は `example.com/app/api.CreatePost` に当たります
- どのシンボルにも当たらない対象は、守られていないと報告されます。メッセージにもそう書かれます

宣言はテストの doc コメントの1行 `guards: <invariant>` です。`<invariant>` は、`hadome explain` やメッセージが呼ぶとおりに書きます。

- 製品固有の不変条件なら `id`
- それ以外は `<type> <target>`。対象が複数なら `<type> <a>,<b>`

たまたま対象を2回呼んでいるだけのテストも、守るものとして数えます。宣言を要らないようにする代わりに、この数え違いは受け入れます。

### `tests/invariant-unguarded`

- **見つけるもの**: 設定で有効にした不変条件のうち、守る有効なテストが無いもの
- **なぜ困るか**: 不変条件は書いてあるのに、何もそれを守らせていません
- **直し方**: 不変条件を確かめるテストを書きます。形のある組み込みの種類なら、それで済みます。それ以外の種類と製品固有の不変条件は、doc コメントに `guards:` を足します
- アンカーは不変条件です。そのため、テストがどう動いても、違反は版をまたいで照合されます
- base と比べるので、テスト無しで新しい不変条件を有効にすると後退になります。base で既に守られていなかった不変条件は止めません
- 守りを失った場合も、同じ違反になります。例: 最後に守っていたテストが消える、スキップされる、形に合わなくなる、`guards:` の行を失う。どれも、base で守られていた不変条件が head で守られていなくなるので、新しい違反として後退になります
- 守りを別のテストに移しても、不変条件は守られたままなので何も変わりません
- 不変条件そのものを設定から消すことは、このルールでは扱いません。`config/loosened` が扱い、終了コード `3` を返します。不変条件をやめるかどうかは人が決めることだからです
- `3` を返すのは、消す変更の1回だけです。その変更が基準のブランチに入った後は、不変条件は単に無いだけになり、後の変更は `0` を返します

（不変条件、守るテスト）の組に対する測るルールは作りません。このルールとまったく同じ場面で働くからです。

## 不変条件の候補

`hadome check` は、変更が足した**不変条件の候補**を一覧にします。候補はふつう不変条件を持つ場所です。

| 場所 | 候補の種類 |
|---|---|
| 何かを作る操作 | `idempotent` |
| 書き出しと読み込みの組 | `round-trip` |
| 削除 | `erasable` |
| 利用者やテナントで絞った読み出し | `isolated` |

- 候補は参考情報で、終了コードは変えません
- `hadome suggest` はすべての候補を出します。候補の見つけ方は [suggest.ja.md](suggest.ja.md) にあります

エージェント向けの指示のブロックは、大事な振る舞いに当たる候補を人に提案するよう、エージェントに伝えます。そのため、誰もコマンドを実行しなくても、人は候補を知ることができます。

## メッセージ

違反にはすべて、エージェント向けに書いた `why` と `fix` が付きます。中身は、何が起きたか、なぜ困るか、それを解消するいちばん小さな変更です。上の文章がそのメッセージの出発点になります。

違反の文言は、シンボルを設定で名指すのと同じ形で書きます。ユニットのパスの最後の要素と名前です。例: `example.com/app/store.Append` は `store.Append`。`size/` と `comments/` も同じ形です。base と照らし合わせるときは、省かない ID を使います。

危険な書き方の違反（`no-clock`、`no-sleep`、`always-true`、`no-mock`）の `message` には、見つけたコードを1行で書きます。何行にもわたる呼び出しは最初の行だけを書き、80文字を超えるところは切ります。省いたところには「…」を付けます。例: `test waits by sleeping: setTimeout(() => { …`。base と照らし合わせるときは、省かないコード全体を使います。

## 自己テストの事例

各ルールには、少なくとも次の事例が付きます。

| `tests/no-sleep` | 新しい sleep は落ちる · テスト以外のコードの sleep はこのルールの仕事ではない · sleep するヘルパーをもう1回呼んでも新しい sleep にならない |

## 不変条件

1. 守るものを変えずにテストを動かす・名前を変える・まとめても、これらのルールは落ちません
2. 常にスキップされるテストは、何かを守るものとして数えません。一部の場合だけ（あるプラットフォームで、あるフラグの下で）自分をスキップするテストは守ります。そのスキップにも理由が要ります
3. どのルールも base に既にあるものを理由に変更を落としません
4. これらのルールは特定できないものを報告します。黙って通しません

## 意図して入れなかったもの

- **テストが*正しい*かを確かめること。** 近づけるのはミューテーション解析だけで、`tests/` のルールの外に置きます
- **テストから本物の外部サービスを呼ぶことを止めるルール（`tests/no-network`）。** アダプタはそうした呼び出しを特定できないので、確実に言える形で止められません
- **テストの速さ。** 独自の設計を持つ別のルール群に属します
- **守る範囲を広げないテストを止めること。** 対象がすべてほかのテストに守られていても、別の入力や別の観点を確かめる正当なテストと見分けられません
- **呼び方（対象・回数・スコープ）が同じテストを重複とみなすこと。** 入力だけが違う正当なテスト（`TestAddPositive` と `TestAddNegative` など）が引っかかります
